# 랩미팅 슬라이드별 내용 초안

[발표 구성 계획](lab-meeting-presentation-plan.md)을 바탕으로 작성한 12장 분량의 본문·도식·발표자 설명이다. 실제 PPT 제작 전 검토용이다. 도입 이유는 설계 목표를 정리한 초안이며, 실제 개발 계기는 발표자의 경험에 맞춰 수정한다. 성능·시간 절감 수치는 아직 넣지 않는다.

## 1. 논문을 읽고, 근거를 남기고, 연구로 연결하기

### 화면 문구

**AI 연구 보조 작업 체계의 설계와 구현**

논문 읽기 → 근거 정리 → 다음 연구 질문

**핵심 목표: 읽은 내용을 다시 찾아 쓰고, 다음 연구로 이어가기**

### 그림

PDF 아이콘 → 근거가 붙은 리뷰 → 연구 질문 카드. 각 요소 아래에 “원문”, “기록”, “다음 행동”을 붙인다.

### 발표 설명

“이번에 만든 것은 논문을 읽고 정리하는 작업을 후속 연구와 연결하는 체계입니다. AI에게 작업을 맡길 때 읽는 순서, 남길 기록, 검증 기준을 함께 정했습니다. 오늘은 왜 만들었는지, 어떤 연구 작업을 도와주는지, 현재 어디까지 구현했는지를 설명드리겠습니다.”

## 2. 왜 이 체계를 만들었나?

### 화면 문구

**연구 기록을 남기는 것에서, 다시 활용하는 것으로**

- **기록 연결:** 원문·리뷰·개념·아이디어를 함께 찾는다.
- **근거 확인:** AI가 정리한 주장과 수치를 원문에서 확인한다.
- **후속 작업:** 읽은 내용에서 조사할 질문과 실험 방향을 정한다.

하단: **시간 절감과 정확도 향상은 앞으로 평가할 기대효과다.**

### 그림

세 가지 문제와 대응을 나란히 표시한다.

흩어진 기록 → 논문별 연결 / 출처 확인 어려움 → 원문 위치 기록 / 후속 질문 누락 → 다음 작업 연결

### 발표 설명

“도입 이유는 세 가지로 정리했습니다. 첫째는 흩어진 기록을 다시 찾고 활용하는 것입니다. 둘째는 AI가 정리한 내용의 근거를 확인하는 것입니다. 셋째는 읽은 내용을 다음 질문으로 연결하는 것입니다. 이런 문제를 다루도록 설계했지만, 실제로 시간이 얼마나 줄고 정확성이 얼마나 좋아지는지는 별도 평가가 필요합니다.”

### 제작 시 보완

실제 개발 계기 한 문장을 추가한다. 예: 발표자가 직접 겪은 기록 검색이나 리뷰 확인의 어려움. 경험이 확인되지 않은 시간·빈도·오류 사례는 넣지 않는다.

## 3. AI에게 무엇을 어떻게 맡기는가?

### 화면 문구

**연구 작업 체계 = 작업별 지침 + 순서 + 기록 + 검증**

- **작업별 지침:** 무엇을 읽고 어떻게 정리할까?
- **다음 작업 안내:** 현재 요청 다음에 무엇을 할까?
- **기준 기록과 검증:** 무엇을 남기고 어떤 조건에서 완료할까?

하단: **연구자는 논문 선택, 이해 확인, 아이디어 진행을 결정한다.**

작은 용어 설명: “하네스: 이 요소들을 연결한 구조 / 스킬: 각 작업의 지침”

### 그림

가운데 “연구 요청 → 작업 수행 → 결과 기록”을 두고 지침·기록·검증을 연결한다. 아래에 연구자의 결정 지점들을 배치한다. 전체 파일 구조나 모든 스킬명을 넣지 않는다.

### 발표 설명

“하네스라는 용어는 연구 작업 체계라고 이해하시면 됩니다. 예를 들어 논문 리뷰에는 읽는 순서와 반드시 확인할 항목이 있고, 결과를 남기는 형식과 완료 기준이 있습니다. 스킬은 이런 작업별 지침입니다. 시스템은 현재 요청에 맞는 지침을 연결하고 기록을 검사합니다. 논문 선택이나 아이디어 진행처럼 연구 판단이 필요한 지점은 연구자가 결정합니다.”

## 4. ① 무엇을 읽을지 정한다

### 화면 문구

**입력: 관심 주제 또는 논문 PDF·링크**

후보 탐색 → 연구자 선택 → 메타데이터·중복 확인 → 등록

**남는 기록: 원문 PDF · 읽기 대기열 · 논문 기본 정보**

하단: “일일 후보는 CV·멀티모달·관심 분야 각 1편. 채택 전에는 채팅으로 제시한다.”

### 그림

후보 카드 3개에서 하나를 선택해 PDF·대기열·기본 정보로 연결한다. 직접 올린 PDF는 등록 단계로 들어오는 별도 입력 화살표로 표시한다.

### 발표 설명

“시작점은 두 가지입니다. 제가 논문을 직접 올리거나, 시스템이 관심 분야의 후보를 제시하는 것입니다. 일일 후보는 세 분야에서 한 편씩 제시하며 발표·게재 여부를 확인하도록 했습니다. 후보를 제시했다는 이유만으로 모두 저장하지는 않습니다. 연구자가 선택하면 기본 정보와 중복을 확인하고 원문과 읽기 대기열에 등록합니다.”

### 보조 표기

관련 지침: `daily-digest-loop`, `paper-search`, `paper-scheduler`.

목록 관리와 별도 요약 요청에는 `keep-list`, `paper-favorites`, `paper-summary`를 사용한다. 이 세 가지는 반드시 순서대로 수행하는 단계가 아니다.

## 5. ② 주장과 근거를 함께 읽는다

### 화면 문구

**입력: 논문 원문**

1. **전체 파악:** 문제·핵심 주장·읽을 가치 확인
2. **방법·실험 확인:** 입력·처리·출력과 비교 결과 확인
3. **비판적 정리:** 주장 범위·한계·재현 조건 확인

**남는 기록: 심층 리뷰 · 방법 구조도 · 주장–근거 표**

하단: “수치와 사실에는 원문 위치를 붙이고, 추론은 구분한다.”

### 그림

3단계 읽기 옆에 “입력 → 주요 처리 → 출력”의 작은 구조도를 둔다. 아래에 다음 형식의 표 한 행을 넣는다.

| 주장 | 원문 근거 | 확인된 결과 | 남은 한계 |
|---|---|---|---|
| 실제 사례 선정 후 입력 | 절·표·쪽 번호 | 실제 결과 | 근거가 보여주지 못한 범위 |

이 표의 빈칸은 사례 준비 항목이며 최종 발표에는 검증된 내용으로 교체한다.

### 발표 설명

“리뷰에서는 먼저 전체 문제를 파악하고, 다음으로 방법과 실험을 확인하며, 마지막으로 주장 범위와 한계를 정리합니다. 중요한 점은 설명과 근거를 함께 남긴다는 것입니다. 수치에는 표나 페이지 위치를 붙이고, 원문에 없는 설정은 미기재라고 표시합니다. 방법 구조도도 실제로 확인한 처리 과정을 바탕으로 작성합니다.”

### 보조 표기

관련 지침: `paper-review`, `review-index`. 5축 분석 항목의 자세한 설명은 필요하면 부록에 넣는다.

## 6. ③ 읽은 내용을 내 지식으로 남긴다

### 화면 문구

**입력: 리뷰에서 발견한 개념과 관련 논문**

개념 후보 초안 → 연구자의 설명·수정 → 이해 확인 → 공부노트

**남는 기록: 확인한 이해 · 근거가 있는 논문 관계**

하단: “AI가 작성한 초안은 연구자의 이해로 자동 인정하지 않는다.”

### 그림

초안 카드와 공부노트 사이에 “연구자 확인” 노드를 둔다. 옆에는 논문 3개를 연결한 작은 관계 지도를 배치하고 각 선에 “공유 방법”, “확장”, “비교”처럼 실제 확인한 관계만 붙인다.

### 발표 설명

“리뷰에서 개념 후보를 뽑을 수는 있지만, AI가 쓴 문장만으로 제가 이해했다고 볼 수는 없습니다. 제가 설명하거나 내용을 수정하고 공부노트로 반영해 달라고 요청한 뒤에 학습 기록으로 남기도록 했습니다. 논문 사이의 관계도 원문을 확인합니다. 지도에 연결돼 있다는 이유만으로 인용이나 영향을 확정하지는 않습니다.”

### 보조 표기

관련 지침: `concept-note`, `related-work`, `paper-relations`, `graphify`.

## 7. ④ 아이디어를 세 관점에서 검토한다

### 화면 문구

**입력: 연구 가설 · 반증 조건 · 관련 문헌**

기획 구체화 → 문헌 근거 확인 → 같은 검토 자료 고정

- **방법:** 설계가 가설을 검증할 수 있는가?
- **재현성:** 다른 사람이 같은 조건으로 확인할 수 있는가?
- **새로움:** 기존 연구와 무엇이 다른가?

**남는 기록: 검토 결과 · 보완점 · 연구자의 진행 결정**

### 그림

동일한 자료에서 세 검토 역할로 분기한 뒤 종합 단계로 합친다. 마지막에는 “연구자: 진행 / 보류 / 폐기”를 배치한다. 세 검토자의 투표로 승인된다는 그림은 사용하지 않는다.

### 발표 설명

“아이디어는 먼저 가설과 반증 조건을 구체화하고 문헌 근거를 확인합니다. 그다음 같은 버전의 자료를 세 검토 역할에 제공합니다. 방법 검토는 가설을 검증할 수 있는 설계인지, 재현성 검토는 다시 확인할 조건이 갖춰졌는지, 새로움 검토는 기존 연구와의 차이를 봅니다. 결과를 종합하되 최종 진행 결정은 연구자가 합니다.”

### 보조 표기

관련 지침: `thought-experiment-critique`, `critical-validation`. 자료 버전을 고정하는 해시의 기술 설명은 부록에 둔다.

## 8. ⑤ 부족한 근거를 더 찾고 작은 실험을 한다

### 화면 문구

**추가 문헌 조사**

질문 고정 → 해결 방법·참고문헌·반대 근거 탐색 → 별도 원문 확인

결과: **비교표 · 지지/반대 근거 · 남은 질문**

**승인된 작은 실험**

연구자 승인 → 성공·반증 기준 확인 → 실행·결과 기록

결과: **실험 설정 · 실행 기록 · 관찰 결과**

하단: “조사 완료 ≠ 아이디어 승인 ≠ 실험 성공”

### 그림

좌우 두 경로로 조사와 실험을 나눈다. 조사 경로 안에는 세 탐색 역할과 별도의 근거 확인 역할을 표시한다. 실험 경로 입구에는 “승인 필요”를 표시한다. 조사에서 실험으로 자동 진행하는 화살표는 사용하지 않는다.

### 발표 설명

“문헌 조사와 실험은 완료 기준이 다릅니다. 문헌 조사에서는 해결 방법, 참고문헌, 반대 근거를 나눠 찾고 별도 역할이 원문을 확인합니다. 조사 완료는 이런 근거를 정리했다는 뜻입니다. 실험은 연구자가 승인한 범위에서 성공과 반증 기준을 정한 뒤 수행합니다. 조사 작업이 끝났다고 아이디어가 승인되거나 실험이 성공한 것은 아닙니다.”

### 보조 표기

문헌 조사 도구: `research_todo.py`. 실험 지침: `thought-experiment-runner`.

문헌 탐색의 세 역할과 앞 장의 방법·재현성·새로움 검토 역할은 서로 다르다.

## 9. ⑥ 작업을 관리하고 다른 환경에 적용한다

### 화면 문구

**세 화면으로 작업과 기록을 찾아본다**

- **하네스:** 어떤 작업을 언제 사용할지 확인
- **논문 목록:** 원문·리뷰·읽기 상태 확인
- **사고실험:** 가설·검토·조사·실험 기록 확인

**공유: 작업 지침과 기본 구조를 다른 환경에 적용**

하단: “화면은 기록을 보여주고, 실제 작업 실행은 별도 실행기가 담당한다.”

### 그림

세 화면에서 설명할 부분만 잘라 크게 배치한다. 하네스는 탭과 단계 상세, 논문 목록은 한 카드의 원문·리뷰 버튼, 사고실험은 가설과 기록 링크를 사용한다. 설치는 작은 별도 상자에 “미리보기 → 충돌 확인 → 적용”으로 표시한다.

### 발표 설명

“운영 화면은 세 가지로 나눴습니다. 하네스 화면에서는 작업별 지침과 실행 순서를, 논문 목록에서는 원문과 리뷰를, 사고실험에서는 가설과 검토 기록을 확인합니다. 화면 자체가 모든 작업을 실행하는 것은 아닙니다. 리뷰 요청은 로컬 실행기와 연결하고, 다른 환경에 적용할 때는 기존 설정과 충돌하는 파일을 먼저 확인하도록 했습니다.”

## 10. 논문 한 편으로 따라가 보기

### 화면 문구

**사용 흐름 예시: 같은 논문이 다음 작업으로 이어지는 과정**

논문 선택 → 원문 정독 → 근거가 붙은 리뷰 → 개념 후보 → 후속 질문

각 단계에서 확인할 것:

- 리뷰의 주장을 원문에서 찾을 수 있는가?
- 개념을 연구자가 설명하고 수정할 수 있는가?
- 후속 질문의 기존 연구와 반대 근거를 찾을 수 있는가?

### 그림

한 논문 제목을 첫 카드에 놓고, 원문 한 부분·리뷰 한 행·개념 후보 한 항목·후속 질문 한 문장을 연결한다. 화면 전체 캡처나 서로 다른 논문의 예시를 섞지 않는다.

### 발표 설명

“전체 흐름을 한 논문으로 설명하면 이렇게 됩니다. 논문을 선택하고 원문을 읽어 주장과 근거를 정리합니다. 여기서 반복해서 사용할 개념은 후보로 남기고 제 이해를 확인합니다. 마지막으로 어떤 조건에서 결과가 달라지는지와 같은 후속 질문을 만들고 관련 근거를 더 찾습니다. 각 단계에서 이전 기록을 다시 사용할 수 있도록 연결한 것이 핵심입니다.”

### 사례 준비 상태

이 장은 현재 **사용 흐름 예시**다. 실제로 이 경로를 모두 완료한 사례라고 주장하지 않는다. 최종 PPT 제작 시 원문과 최종 리뷰를 확인한 논문 한 편을 선정한다. 확인된 공부노트나 후속 질문이 없다면 해당 카드에는 “후보” 또는 “다음 작업 예시”를 표시한다. 논문별 실제 수치와 근거 위치는 사례 선정 이후 작성한다.

## 11. 현재 어디까지 구현했나?

### 화면 문구

**구현된 기능과 실제 사용 결과를 구분한다**

| 구분 | 현재 범위 |
|---|---|
| 구현 | 작업별 지침·순서 안내, 세 HTML 화면, 기록 검증, 리뷰 실행기, 조사 배분·설치 도구 |
| 확인 | 앞선 도구 단위 테스트와 화면 동작 확인, 이번 디자인의 화면 렌더링 확인 |
| 다음 확인 | 실제 리뷰·다중 조사 작업의 전체 실행, 내용 정확성, 사용성과 효과 |

하단: “도구 검사 통과는 논문 내용의 정확성이나 연구 성과를 입증하지 않는다.”

### 그림

“구현”, “확인”, “다음 확인”의 세 열을 사용한다. 아직 실행하지 않은 자동화에 성공 표시를 붙이지 않는다. 테스트 수와 항목은 제작 시 실행 기록을 대조한 경우에만 표기한다.

### 발표 설명

“현재는 지침과 화면, 기록 검증, 실행을 연결하는 도구들을 구현했습니다. 앞선 작업에서 도구 단위 테스트와 화면 동작을 확인했고, 이번에는 디자인을 적용한 화면을 살펴봤습니다. 실제 논문 리뷰와 다중 조사 작업이 처음부터 끝까지 완료되는지, 결과 내용이 정확한지는 추가 확인이 필요합니다. 구현과 실제 연구 효과를 구분해서 보고드리려 합니다.”

## 12. 앞으로 무엇을 평가할 것인가?

### 화면 문구

**실제 연구 작업에 적용해 네 가지를 확인한다**

1. **근거 정확성:** 주장·수치·원문 위치가 맞는가?
2. **내용 누락:** 방법·실험·한계의 필수 항목이 빠지지 않는가?
3. **기록 재사용:** 이전 리뷰에서 근거를 찾고 다음 질문에 연결할 수 있는가?
4. **작업 부담:** 시간과 수정 횟수, 사용성은 어떻게 달라지는가?

교수님께 드릴 질문:

- 연구실 리뷰·아이디어 검토에 반드시 넣을 기준은 무엇인가?
- 어떤 실제 연구 과제에 먼저 적용하면 유용성을 확인할 수 있는가?

### 그림

평가 기준 네 개를 2×2 카드로 표시한다. 하단에는 “기록 연결 → 근거 확인 → 다음 연구”의 짧은 흐름을 다시 보여준다.

### 발표 설명

“다음 단계는 실제 연구 작업에 적용해서 평가하는 것입니다. 근거가 맞는지, 중요한 내용이 빠지지 않는지, 기록을 다시 사용할 수 있는지, 시간과 수정 부담이 어떻게 달라지는지를 보려 합니다. 연구실에서 중요하게 보는 리뷰와 검토 기준, 그리고 처음 적용할 연구 과제에 대해 의견을 받고 싶습니다.”

## 선택 부록 — 새 사용자의 실제 시작 순서

슬라이드 본문: **Git·Python·에이전트 설치/로그인 → 저장소 clone → 준비 검사 → 지침·검색 연결 확인 → 첫 논문 수집/정독**.

데모 명령은 저장소 루트에서 `python3 -B .scripts/bin/onboarding_check.py --host codex`, `python3 -B .scripts/bin/verify_harness.py`, `codex` 순서로 실행한다. Claude는 호스트 옵션과 실행 명령을 바꾼다. 에이전트 입력란에서 규칙 확인과 메타데이터 조회를 먼저 요청한다. 정확한 요청문은 [온보딩 안내의 첫 실행](onboarding.md#6-첫-실행과-작동-확인)을 사용한다.

발표자 설명: “설치기는 다른 프로젝트에 스킬을 옮기는 도구입니다. 우리 저장소를 처음 쓰는 사람은 clone한 폴더에서 에이전트에 로그인하고 준비 검사를 합니다. 검사 뒤 실제 모델 응답과 검색을 확인한 다음 논문 작업을 시작합니다.”

확인 한계: 준비 검사 통과와 MCP 실제 연결·원문 정독 완료는 별도로 보여준다. 공유 전 로컬 변경을 브랜치에 반영하고 새 clone에서 검사해야 한다.
