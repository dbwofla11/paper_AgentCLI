# 랩미팅 발표자료 계획 — 논문 읽기와 연구 검증을 연결하는 작업 체계

페이지별 본문 문구·도식·발표 설명은 [슬라이드별 내용 초안](lab-meeting-slide-content.md)에 정리했다.

## 1. 발표 목표와 범위

교수님과 연구실 구성원이 처음 보더라도 다음 질문에 답할 수 있게 한다.

1. 왜 만들었는가?
2. 어떤 연구 작업을 도와주는가?
3. 각 단계에서 무엇이 입력되고 무엇이 남는가?
4. AI가 수행하는 작업과 연구자가 판단하는 지점은 어디인가?
5. 지금 구현된 범위와 앞으로 평가해야 할 부분은 무엇인가?

발표 시간은 **15분 내외, 본문 12장 + 선택 부록**으로 가정한다. 현재 요청은 PPT 제작 전 구성 계획이다. 실제 PPT 파일과 발표 대본은 후속 제작 대상으로 둔다.

제목 제안: **논문을 읽고, 근거를 남기고, 연구로 연결하기**

부제: **AI 연구 보조 작업 체계의 설계와 구현**

핵심 문장: “AI에게 연구 작업을 맡길 때, 읽는 순서·남길 기록·검증 기준·연구자의 결정 지점을 함께 정했습니다.”

## 2. 도입 이유를 설명하는 방식

아래는 저장소의 근거 규칙과 작업 목표에서 정리한 **발표용 도입 배경**이다. 사용자가 실제 겪은 사례와 시간이 확인되면 해당 사례로 교체한다. 연구실 전체가 겪었다고 단정하지 않는다.

| 연구 작업에서 생길 수 있는 문제 | 설계 목표 | 대응하는 기능 |
|---|---|---|
| PDF, 요약, 아이디어 기록이 흩어져 다음에 다시 찾기 어렵다 | 같은 논문과 연구 질문을 연결해 다시 쓸 수 있게 한다 | 논문 목록, 원문·리뷰 연결, 관계 확인 |
| AI가 정리한 설명의 출처와 정확성을 확인하기 어렵다 | 주장과 수치에 원문 위치를 붙인다 | 원문 정독, 주장–근거 표, 구조화 기록 검증 |
| 논문을 읽은 기록이 공부노트와 후속 아이디어로 이어지지 않는다 | 읽은 내용을 확인된 이해와 연구 질문으로 연결한다 | 개념 후보, 사용자 확인, 학습 기록 |
| 아이디어의 지지 근거만 모으거나 검토 기준이 매번 달라질 수 있다 | 대안·반대 문헌도 조사하고 같은 자료로 여러 관점을 검토한다 | 문헌 조사, 방법·재현성·새로움 검토 |
| 작업 진행과 결정 근거를 다시 파악하기 어렵다 | 단계별 상태와 산출물을 남긴다 | 조사 대기열, 실행 기록, 대시보드 |

발표에서 말할 이유: “논문을 읽고 난 뒤 근거와 생각을 다시 찾아 활용할 수 있도록, 연구 작업의 연결과 기록 방식을 정리하고 싶었습니다.” 실제 개발 동기가 다르면 사용자 경험에 맞춰 수정한다.

시간 절감, 오류 감소, 연구 성과 향상은 **기대효과**다. 비교 실험이나 사용자 평가 없이 달성한 성과로 표시하지 않는다.

## 3. 직관적인 용어

| 구현 용어 | 발표에서 먼저 쓸 표현 | 첫 설명 |
|---|---|---|
| 하네스 / harness | 연구 작업 체계 | 작업 순서, 기록 형식, 검증 기준을 연결한 구조 |
| 하네싱 / harnessing | AI 작업 절차 설계 | AI에게 무엇을 어떤 순서로 맡길지 정하는 일 |
| 스킬 / skill | 작업별 지침 | 논문 읽기, 문헌 조사 등 각 작업의 방법과 완료 기준 |
| 라우팅 / routing | 다음 작업 안내 | 현재 요청에 맞는 작업별 지침을 선택 |
| 페르소나 / persona | 검토 역할 | 방법, 재현성, 새로움 등 관점을 나눈 검토 |
| 정본 / canonical source | 기준 기록 | 같은 정보를 여러 곳에 다르게 저장하지 않도록 기준으로 삼는 파일 |
| JSON / schema | 정해진 항목의 기록 / 기록 형식 | 컴퓨터가 누락과 상태를 확인할 수 있도록 항목을 정리 |
| 근거 동결 / SHA-256 | 검토 자료 고정 | 검토자들이 같은 버전의 자료를 받았는지 확인 |
| Graphify | 논문·개념 연결 지도 | 확인한 논문과 개념의 관계를 탐색 |
| 로컬 브리지 | 내 컴퓨터의 작업 실행기 | 화면의 요청을 실제 에이전트 실행으로 연결 |
| 온보딩 | 다른 사람의 환경에 적용 | 기존 설정을 보존하며 지침과 기본 구조를 설치 |

슬라이드 본문에는 쉬운 표현을 먼저 쓰고 실제 스킬 이름은 작은 보조 표기나 부록에 둔다. “자동 심사 승인”, “논문 내용 완전 이해”, “연구 성공 보장” 같은 표현을 쓰지 않는다.

## 4. 연구 단계별 여섯 범주

| 발표 범주 | 질문 | 핵심 작업 | 대표 산출물 |
|---|---|---|---|
| ① 논문 찾기·모으기 | 무엇을 읽을까? | 후보 제안, 사용자 선택, 메타데이터 확인, 중복 확인 | PDF, 읽기 대기열, 논문 기본 정보 |
| ② 논문 읽기·근거 정리 | 무엇을 주장하고 무엇으로 증명했나? | 3패스 정독, 방법 구조도, 주장–근거 대응, 실험·한계 정리 | 심층 리뷰, 5축 분석, 원문 위치 |
| ③ 이해 기록·논문 연결 | 무엇을 배웠고 어디에 연결되나? | 개념 후보, 사용자 이해 확인, 공부노트, 문헌 관계 확인 | 확인된 학습 기록, 근거가 있는 관계 |
| ④ 아이디어 검토 | 이 가설을 왜 진행할까? | 가설·반증 조건, 기획 질문, 문헌 조사, 세 관점의 독립 검토 | 비판 검토 결과, 보완점, 사용자 결정 |
| ⑤ 추가 조사·작은 실험 | 다음에 무엇을 확인할까? | 솔루션·참고문헌·반대 근거 탐색, 별도 원문 확인, 승인된 실험 | 비교표, 조사 보고서, 실험 기록 |
| ⑥ 작업 관리·공유 | 어떻게 지속해서 쓰고 함께 쓸까? | 단계 안내, 상태 조회, 기록 검증, 실행 연결, 설치·진단 | 세 HTML 화면, 오류 기록, 적용 도구 |

탐색·수집의 요약/즐겨찾기는 독립 요청으로 설명한다. 모든 작업을 항상 처음부터 끝까지 실행한다고 보여주지 않는다.

## 6. 예시와 증거 준비

- 사례 논문은 **원문 위치와 최종 리뷰가 확인된 한 편**을 고른다. 검토하지 않은 JSON의 메타데이터만으로 완성 사례를 만들지 않는다.
- 적절한 완성 리뷰가 없으면 “사용 흐름 예시”라고 표시하고, 각 산출물은 예시와 실제 파일을 구분한다.
- 학습 노트나 아이디어의 사용자 승인 상태를 발표용으로 임의 변경하지 않는다.
- 실제 리뷰 한 행: 핵심 주장 / 원문 근거 위치 / 확인된 결과 / 보여주지 못한 것.
- 방법 구조도는 입력 → 주요 처리 → 출력에 실험·손실 등 필요한 가지를 붙인다. 재구현 설명은 원문에 확인된 내용만 쓴다.
- 실시간 AI 실행 대신 저장된 화면과 기록으로 설명할 수 있게 한다. 실행 데모는 별도 승인과 준비가 있을 때만 구성한다.
- 현재 파일 수는 수집 규모로만 표시한다. 리뷰 완료 수나 품질 평가 결과로 바꿔 말하지 않는다.

## 7. 현재 구현 범위를 설명하는 기준

**구현된 항목:** 작업별 스킬과 순서 안내, 정본에서 생성한 세 HTML 화면, 원문 링크·리뷰 표시, 구조화 기록과 검증기, 조사 대기열과 작업 배분 도구, 로컬 리뷰 실행기, 설치·진단 도구.

**현재까지 확인한 범위:** 앞선 구현의 구조 검사·도구 단위 테스트와 HTML 동작 확인. 이번 디자인 수정은 화면 렌더링을 살펴봤으며 별도의 테스트는 실행하지 않았다. 논문 내용의 사실 정확성이나 연구 효과를 단위 테스트 통과로 입증했다고 말하지 않는다.

**아직 주장하지 않을 내용:** 실제 논문 리뷰 자동 실행의 종단간 성공, 다중 조사 작업의 실제 완주, 시간·비용 절감, 학습 향상, 실험 성공. 해당 실행 기록·평가가 준비된 경우에만 업데이트한다.

HTML은 주로 기록과 절차를 보여준다. 리뷰 작업 요청에는 로컬 실행기가 필요하다. 조사 완료, 아이디어 승인, 실험 성공은 각각 다른 상태다. 문헌 탐색 역할 3개와 아이디어 비판 검토 역할 3개도 서로 다른 역할이다.

## 8. PPT 표현과 디자인

- 16:9, 한 장에 한 메시지, 본문 3줄 또는 3개 핵심 항목을 기본으로 한다.
- 발표 제목 32–40pt, 본문 22–26pt. 코드·파일 경로·스킬명을 화면 전체에 나열하지 않는다.
- `docs/design/DESIGN-discord.md`의 짙은 인디고·Blurple·마젠타와 둥근 도형을 사용한다. 화면과 PPT의 시각 언어를 맞춘다.
- 핵심 도식은 PPT 기본 도형과 화살표로 만들어 편집 가능하게 한다. 전체 복잡한 구조도를 매 장 반복하지 않는다.
- 읽기 → 이해 → 검토 → 다음 작업을 단계적으로 보여준다. 선택 실행은 점선, 사용자 결정은 별도 노드, 병렬 작업은 분기로 표시한다.
- 화면 캡처는 사용자가 읽어야 할 부분만 크게 자르고, 설명 표시는 최대 2–3개로 제한한다.
- 결과와 계획을 시각적으로 구분한다. 측정하지 않은 효과에 수치·성공 체크 표시를 붙이지 않는다.

## 9. 평가 계획과 교수님께 받을 피드백

평가 제안: 같은 논문을 대상으로 기존 개인 작업 방식과 이 작업 체계의 결과를 비교한다. 정확성은 원문 대조로, 사용성과 재사용성은 실제 작업 사례로 확인한다. 사용자와 평가 기준을 정한 뒤 실행한다.

| 평가 항목 | 확인 방법 |
|---|---|
| 근거 정확성 | 표본 주장·수치와 원문 위치를 대조 |
| 필수 항목 누락 | 방법·실험·한계 등 사전 항목으로 검사 |
| 기록 재사용성 | 이전 리뷰에서 관련 근거를 찾고 다음 질문에 연결하는 과제 |
| 작업 시간·사용성 | 같은 작업의 소요 시간과 수정 횟수, 사용자 피드백 기록 |

교수님께 질문할 사항:

1. 리뷰와 아이디어 검토에 반드시 들어가야 할 연구실 기준은 무엇인가?
2. 이 체계의 유용성을 확인하기 위해 어떤 실제 연구 과제를 먼저 적용할 것인가?
