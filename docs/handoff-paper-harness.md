# Hand-off: 논문 하네스 대시보드와 자동 리뷰 연결

아래는 최초 작업 요청이다. 현재 구현된 HTML 화면은 `100-views/`에서 관리하며, 실행·갱신 방법은 [화면 관리 안내](../100-views/README.md)를 따른다. 로컬 리뷰 실행기는 `http://127.0.0.1:8765/`에서 새 위치로 연결한다.

```text
paper_AgentCLI의 연구 하네스 작업을 이어서 진행하자. 먼저 저장소 상태를 조사하고, 아래 목표들을 기존 구조와 정본 규칙에 맞춰 설계한 뒤 구현해줘.

## 목표

1. 하네스와 스킬 상태를 보고 관리할 수 있는 대시보드 문서/HTML을 만든다.
   - 현재 하네스 단계와 라우팅, 설치된 스킬 목록, 필수 페르소나, 검증기·테스트 상태, Graphify 동기화 상태를 기존 정본에서 읽어 보여준다.
   - `.agents/skills/`를 스킬의 정본으로 삼고 `.claude/skills/`, `.codex/skills/`는 실제 연결 상태를 검사한다.
   - 상태를 문서에 중복 기록하지 말고 가능한 한 파일·검사 결과에서 산출한다.
   - “관리” 기능은 실제로 가능한 범위를 먼저 구분한다. 정적 HTML만으로 로컬 파일을 수정하거나 명령을 실행할 수 있다고 가정하지 말고, 필요한 로컬 브리지/서비스와 권한 경계를 설계한다.
   - 종합 상태, 실패 항목, 해당 파일 열기, 검증 재실행 또는 안전한 관리 동작을 사용자에게 명확히 보여준다.

2. `paper-library.html`의 `원문 열기` 버튼이 작동하지 않는 버그를 고친다.
   - 생성기, 논문 JSON의 `source.pdf_path`/`source.urls`, 실제 PDF 경로, HTML을 여는 방식(로컬 파일 또는 서버)을 대조해 원인을 확인한다.
   - 저장소 PDF가 있으면 그것을 우선 열고, 없을 때만 유효한 HTTP(S) 원문 URL을 사용한다.
   - 상대경로, URL 인코딩, 새 탭 동작을 검증한다. 링크가 없거나 잘못된 경우 사용자에게 실패 상태를 보여준다.
   - 생성기 수정 후 `paper-library.html` 자체도 다시 생성한다.

3. 미리보기에서 리뷰가 없는 논문에 `리뷰 시작`을 누르면, 정해둔 하네스를 통해 에이전트가 해당 논문을 리뷰하고 결과를 보여주도록 설계·구현한다.
   - 리뷰 필요 여부는 JSON의 `source.review_path`, `structured_review_status`, 실제 리뷰 파일 존재 여부를 기준으로 판정한다.
   - 기존 `paper-review` 스킬과 템플릿의 3패스·근거 규칙·JSON 갱신·인덱스 갱신 절차를 따른다.
   - 클릭한 논문 하나만 작업에 넣고, 대기/실행 중/완료/실패 상태와 중복 실행 방지를 제공한다.
   - 성공 시 리뷰 Markdown, JSON, 인덱스, Graphify 동기화 상태를 검증하고 카탈로그 HTML을 갱신한다. 실패하면 로그와 재시도 가능한 상태를 남긴다.
   - PDF를 실제로 읽을 수 있는 에이전트 런타임/도구인지 확인한다. PDF 읽기나 정해진 리뷰 도구가 없으면 초록만으로 리뷰를 완료 처리하지 말고 명시적으로 중단한다.
   - 브라우저가 임의 shell 명령을 실행하게 하지 않는다. 현재 세션의 에이전트를 직접 호출할 수 있다고 가정하지 말고, 가능한 런타임 훅/API/로컬 브리지부터 확인한다. 존재하지 않는 연동을 만들어냈다고 보고하지 않는다.
   - 실제 자동 리뷰 호출이 현재 환경에서 불가능하면, 확인된 한계와 필요한 런타임 선택을 분리해 보고하고, 우선 안전한 대기열/상태 UI와 테스트 가능한 어댑터 경계까지만 구현한다.

4. 다른 사람도 자신의 저장소에 이 하네스를 자동 적용할 수 있는 온보딩 프로그램을 구축한다.
   - 설치 대상 저장소와 사용 중인 에이전트 환경(Codex, Claude Code 등)을 감지하거나 사용자가 선택하게 한다.
   - 공통 스킬의 정본은 이 저장소 원칙대로 `.agents/skills/`에 두고, 각 호스트가 요구하는 진입점·링크·shim을 생성한다. 호스트별 지원 방식과 심볼릭 링크를 쓸 수 없는 환경의 대안을 확인한다.
   - 하네스 안내 문서, 기본 라우팅/검증 설정, 필요한 폴더 구조를 대상 저장소에 맞게 설치한다. 논문 저장소 전용 경로·규칙과 일반 코딩 저장소에 공통으로 적용할 수 있는 부분을 분리한다.
   - 기존 `AGENTS.md`, `CLAUDE.md`, 설정 파일, 스킬을 무단 덮어쓰지 않는다. 충돌을 미리 보여주고 병합·유지·건너뛰기 선택을 제공한다.
   - `--dry-run`, 멱등 재실행, 설치 manifest/버전 기록, 안전한 업데이트와 제거 방식을 설계한다. 제거는 프로그램이 생성·추적한 파일만 대상으로 한다.
   - 사용자 API 키·credential은 복사하거나 출력하지 않는다. MCP 설정은 비밀이 포함된 실제 설정을 복사하지 말고 안전한 예시/템플릿으로 안내한다.
   - 설치 후 링크·파일·스킬 탐색과 검증기를 점검하는 진단 명령을 제공하고, 깨끗한 임시 저장소와 기존 설정이 있는 저장소 양쪽을 테스트한다.
   - 프로그램이 어떤 파일을 만들거나 수정하는지, 지원 호스트와 제한사항이 무엇인지 문서화한다. 에이전트가 해당 환경에서 실제로 호출 가능한지 검증되지 않았다면 자동 실행 지원을 주장하지 않는다.

5. 사고실험과 연구 아이디어를 리스트로 탐색할 수 있는 HTML 문서를 만든다.
   - `05-ideas/thought-experiments/`의 아이디어 노트와 `04-Projects/thought-experiment-runs/`의 분석 JSON·검증 레지스트리·실험 기록을 연결해 아이디어별 목록을 만든다.
   - 제목, 핵심 가설, 반증 조건, 주제, 마지막 갱신일, 문헌 탐색 여부, 방법/재현성/새로움 심사 상태, 사용자 결정, 실험 진행 상태를 확인 가능한 근거에서 표시한다. 기록이 없으면 미기록으로 표시한다.
   - 제목·가설·주제 검색, 검증/실험 상태별 필터와 정렬을 제공한다. 목록 항목을 누르면 아이디어 원문, 분석 컨텍스트, 심사 결과, 연결 논문과 실험 산출물을 읽을 수 있게 한다.
   - 기존 정본에서 목록을 생성하고 재생성 방법을 제공한다. HTML에 별도의 연구 상태를 수동 관리하지 않는다. 서로 다른 기록의 상태가 충돌하면 충돌 표시와 출처를 보여준다.
   - 기존 Jev 사례의 상태 재조정은 이번 작업 범위에 넣지 않는다. 표시된 상태를 임의로 승인·실험 가능 상태로 변경하지 않는다.
   - 하네스/스킬 대시보드와 논문 라이브러리에서 이 사고실험 HTML로 이동할 수 있도록 내비게이션을 연결한다.

6. 에이전트 전용 연구 TODO와 다중 서브에이전트 문헌 조사 자동화를 구축한다.
   - `docs/agent-research-todo.md`를 시작 문서로 사용한다. 사용자가 지정한 사고실험마다 기존 솔루션과 이를 뒷받침하는 레퍼런스를 찾는 조사 작업을 등록한다.
   - 사고실험 ID/경로, 고정된 brief 버전 또는 해시, 조사 질문, 적용 조건·제약·반증 조건, 기존 논문 ID, 검색 범위, 실행 예산과 결과 경로를 작업 컨텍스트로 전달한다.
   - 주 에이전트는 TODO 배분·상태 관리·결과 종합을 담당한다. 기존 솔루션 탐색, 레퍼런스 추적, 대안·반대 근거 탐색은 독립 서브에이전트에 배분하고, 탐색 후 별도 근거 확인 역할이 원문과 주장 대응을 점검한다.
   - 검색 질의·검색일·실제 출처·포함/제외 이유를 기록하고 최소 두 독립 문헌 소스를 확인한다. 솔루션별 방법, 적용 조건, 비교 대상, 관련 논문 ID·버전과 근거 위치를 연결한다.
   - 기존 논문 수집·문헌 관계 스킬과 JSON 스키마를 재사용한다. 조사 역할은 기존 method/repro/novelty 비판 심사와 구분하며, 검색 결과만으로 비판 검증이 완료됐다고 처리하지 않는다.
   - `todo/queued/running/verifying/completed/failed/needs_input` 상태, 중복 실행 방지, 시간·비용·병렬 실행 한도, 오류·재시도 로그와 부분 결과를 관리한다. 완료는 근거가 확인된 문헌 조사 완료이며 실험 성공이나 아이디어 승인이 아니다.
   - 작업 실행은 앞서 설계한 에이전트 훅/로컬 실행기와 연결한다. 서브에이전트 실행 기능이 없는 환경에서는 대기 상태와 이유를 표시한다.
   - 결과는 솔루션 비교표, 지지·반대 레퍼런스, 근거 위치, 검색 한계와 남은 확인 질문으로 저장한다. 이 작업으로 직접 실험·코드 연구를 실행하거나 사고실험의 승인 상태를 바꾸지 않는다.
   - 사고실험 HTML에서 해당 TODO, 배정 역할, 진행 상태와 조사 결과를 볼 수 있게 한다. 자동화 구현 뒤 상태 정본은 구조화 대기열로 두고 문서/HTML 목록은 그 정본에서 생성한다.

## 작업 순서와 제약

1. `AGENTS.md`, `CLAUDE.md`, 관련 스킬, `docs/Harness-Graph.md`, `docs/Skill-Catalog.md`, `paper-library.html` 생성기, 검증기, 현재 Graphify 상태와 기존 설치/배포 코드를 먼저 확인한다. 코드베이스 질의는 프로젝트 Graphify 규칙에 따라 먼저 조회한다.
2. 작업 전 `git status`를 확인한다. 기존 변경사항은 사용자 작업으로 보고 보존하며, 이번 요청과 무관한 파일을 되돌리거나 정리하지 않는다.
3. 먼저 현황·원인·제안 구조를 짧게 설명한다. 런타임이나 권한 같은 결정이 필요하면 임의로 정하지 말고 그 부분만 질문한다.
4. 구현은 기존 정본과 스킬을 재사용한다. 새 스킬/상태 원장/온보딩 프로그램을 추가한다면 기존 문서와 검사기도 함께 갱신한다. 온보딩은 별도 변경 범위가 크므로 적용 대상, 호스트 지원 범위, 사용자 파일 충돌 처리 계획을 먼저 분명히 한다.
5. 정적 HTML의 기능과 로컬 실행기가 필요한 기능을 구분해 문서화한다. 자동 리뷰가 불가능한 환경에서는 버튼이 성공한 것처럼 보이게 만들지 않는다.
6. 완료 후 생성 HTML을 갱신하고 상대 링크·JavaScript·JSON 검증, 하네스 검사, 자동화 테스트를 실행한다. 코드 변경 시 Graphify도 프로젝트 규칙대로 갱신한다.
7. 온보딩 도구는 임시 디렉터리에서 신규 설치·재실행·기존 파일 충돌·업데이트/제거 동작을 검증한다. 실제 사용자 저장소에는 사용자 확인 없이 설치를 실행하지 않는다.
8. 변경 파일, 자동화되는 범위, 지원 호스트, 남은 런타임 제약, 실행한 검증 결과를 한국어로 요약한다. Git commit/push는 하지 않는다.
```
